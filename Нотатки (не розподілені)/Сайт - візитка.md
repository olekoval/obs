

# Технічне завдання 

## Проект: Персональний веб-сайт-портфоліо для пошуку роботи (No-JS)

### 1. Мета проекту

Створення веб-додатка на базі фреймворку Flask, який виконує роль інтерактивного резюме. Вся логіка додатка, включаючи обробку форм та переходи між сторінками, реалізується **виключно на стороні сервера**.

> ⚠️ **Критичне обмеження:** Використання JavaScript (включаючи сторонні JS-бібліотеки, скрипти, інлайнові події на кшталт `onclick` або AJAX) **категорично заборонено**.

### 2. Функціональні вимоги & Реалізація без JS

Потрібно адаптувати стандартні інтерактивні елементи під роботу без скриптів:

- **Головна сторінка (`/`):** Інтро, стек, кнопки дій.
    
- **Про мене (`/about`):** Професійний профіль та навички.
    
- **Проекти (`/projects`):** Картки проектів.
    
    - _Замість JS-модальних вікон:_ Детальний опис проекту відкривається або на окремій сторінці (`/projects/<id>`), або реалізується за допомогою CSS-хаків (наприклад, через приховані `checkbox` та селектор `:checked`).
        
- **Контакти & Форма зворотного зв'язку (`/contact`):**
    
    - **Валідація форми:** Виконуються виключно вбудовані атрибути HTML5 (`required`, `type="email"`, `pattern`) та фінальна сувора перевірка на бекенді у Flask.
        
    - **Обробка помилок/успіху:** Замість спливаючих вікон (Toast/Alert) використовується механізм **Flask Flash Messages**. Після відправки форми сторінка перезавантажується, і Flask рендерить повідомлення про статус операції безпосередньо в HTML-шаблон.
        

### 3. Технічний стек

- **Back-end:** Python 3.x, Flask, Flask-SQLAlchemy, Flask-WTF (ідеально для генерації та валідації HTML-форм без JS).
    
- **База даних:** SQLite / PostgreSQL.
    
- **Front-end:** HTML5, CSS3.
    
    - _Стилізація:_ Tailwind CSS або Bootstrap (але **виключно їхні CSS-частини**, без JS-компонентів). Для навігаційного меню («гамбургера») на мобільних пристроях використовуватиметься CSS-рішення на базі тексту та тегу `<label>`.
        
- **Шаблонізатор:** Jinja2.
    

### 4. Специфічні обмеження та архітектурні рішення (No-JS)

- **Мобільне меню (Burger Menu):** Відкриття та закриття меню для смартфонів реалізується через прихований HTML-елемент `<input type="checkbox" id="menu-toggle">` та CSS:
    
    CSS
    
    ```
    #menu-toggle:checked ~ .mobile-menu { display: block; }
    ```
    
- **Захист від спаму (No-JS Captcha):** Оскільки популярна Google reCAPTCHA вимагає JS, захист форми реалізується через **Honey-pot field** (приховане CSS-стилями поле, яке бачать і заповнюють лише спам-боти, а Flask відхиляє такі запити) або просте математичне питання, яке генерується на сервері (наприклад: _"Скільки буде 5 + 3?"_).
    
- **Динамічний контент:** Будь-які фільтри проектів (наприклад, за мовами програмування) реалізуються через URL-параметри (наприклад, `/projects?tech=python`). Користувач клікає за посиланням, сторінка перезавантажується, а Flask повертає відфільтрований список із бази даних.
    

### 5. Нефункциональные требования

- **Швидкість та легкість:** Відсутність JS-скриптів гарантує моментальне завантаження сторінок та мінімальний розмір сайту (High Performance / Lighthouse score ~100).
    
- **Доступність (Accessibility):** Сайт за замовчуванням буде максимально доступним для екранних зчитувачів (screen readers).
    
- **Безпека:** Ризик XSS-атак (Cross-Site Scripting) зведений майже до нуля через повну відсутність виконання клієнтських скриптів.
    

## Розбір бізнес-логіки сайту-портфоліо без використання JavaScript  
Оскільки клієнтських скриптів немає, вся логіка побудована на класичному циклі **"Запит (Request) -> Обробка на сервері -> Відповідь (Response)"**. Вся динаміка відбувається через перезавантаження сторінок або відправку HTML-форм.

## 1. Загальна схема взаємодії (Request-Response)

Коли рекрутер або потенційний роботодавець заходить на сайт, взаємодія з Flask відбувається за такою логікою:

1. **Клієнт (Браузер)** відправляє HTTP-запит (GET або POST) на сервер.
    
2. **Flask (Маршрутизатор)** приймає запит і викликає відповідну функцію (View function).
    
3. **Контролер (Логіка)** за потреби звертається до **Бази даних** (наприклад, за списком проектів).
    
4. **Шаблонізатор (Jinja2)** збирає кінцевий HTML-код, підставляючи туди дані з Python.
    
5. **Сервер** повертає готовий HTML браузеру.
    

## 2. Логіка основних бізнес-процесів

Розглянемо детально три головні динамічні процеси на сайті.

### А. Логіка відображення та фільтрації проектів (БЕЗ Ajax/JS)

Замість динамічного приховування карток на сторінці за допомогою JS, ми використовуємо класичну фільтрацію через URL-параметри (Query Parameters).

- **Крок 1 (Запит з фільтром):** Користувач заходить на сторінку `/projects`. Він бачить усі проекти та лінки-фільтри: `[Всі]`, `[Python]`, `[SQL]`.
    
- **Крок 2 (Клік по фільтру):** Користувач клікає на кнопку `[Python]`. Браузер переходить за посиланням `/projects?tech=python`.
    
- **Крок 3 (Обробка на сервері):** * Flask перевіряє наявність параметра: `tech = request.args.get('tech')`.
    
    - Якщо параметр є, робиться SQL-запит до БД з умовою `WHERE tech_stack LIKE '%python%'`.
        
    - Якщо параметра немає — дістаються всі проекти.
        
- **Крок 4 (Рендеринг):** Jinja2 отримує відфільтрований список проектів, циклом `{% for project in projects %}` формує HTML і віддає користувачу.
    

### Б. Логіка обробки форми контактів та захисту від спаму (No-JS)

Найважливіша частина, де зазвичай використовують JS. У нашому випадку весь ланцюжок виглядає так:

Plaintext

```
[Користувач заповнює форму] 
           │
           ▼
[Натискає кнопку "Надіслати" (HTTP POST)]
           │
           ▼
┌────────────────── Flask Бекенд ──────────────────┐
│ 1. Перевірка Honeypot (Чи пусте приховане поле?)  │
│    - Якщо заповнене -> Спам-бот -> Скидання запиту│
│ 2. Валідація даних (Email валідний? Текст є?)    │
│    - Якщо помилка -> Flask Flash -> Повернення    │
│ 3. Збереження в БД / Відправка в Telegram/Email  │
│ 4. Генерація Flask Flash ("Повідомлення успішне")│
└──────────────────────────────────────────────────┘
           │
           ▼
[Перенаправлення (Redirect 302) на /contact з новим HTML]
```

- **Деталі захисту від спаму (Honey-pot):** В HTML додається поле `<input type="text" name="username_real" class="hidden-field">`. За допомогою CSS ми ховаємо його від очей людини (`display: none;`). Спам-боти зчитують голий HTML і заповнюють усі поля поспіль. Якщо Flask бачить, що `request.form.get('username_real')` не пусте — додаток просто ігнорує запит.
    

### В. Логіка сповіщень користувача (Flask Flash Messages)

Оскільки ми не можемо показати красиве спливаюче віконце (Toast notification) через JS після успішної відправки форми, бізнес-логіка використовує сесії:

1. Після успішної обробки форми контактів, викликається функція `flash('Ваше повідомлення успішно надіслано!', 'success')`.
    
2. Бекенд робить `redirect(url_for('contact'))`. Це важливо (принцип POST-Redirect-GET), щоб при випадковому оновленні сторінки користувачем форма не відправилася вдруге.
    
3. При новому завантаженні сторінки Jinja2 перевіряє: `{% with messages = get_flashed_messages() %}`. Якщо вони є, сервер вбудовує блок із повідомленням безпосередньо вгорі сторінки.
    

## 3. Схема Бази Даних (Зв'язки)

Для сайту-візитки потрібна мінімалістична БД (навіть 2-3 таблиці). Ось базова логіка сутностей:

- **Таблиця `Project` (Проекти):**
    
    - `id` (Primary Key)
        
    - `title` (Назва проекту)
        
    - `description` (Опис)
        
    - `tech_stack` (Рядок або зв'язана таблиця тегів, наприклад: "Flask, PostgreSQL, Tailwind")
        
    - `github_link` (Посилання на код)
        
    - `live_link` (Опціонально — лінк на деплой)
        
    - `date_created` (Для сортування нових проектів вище)
        
- **Таблиця `ContactMessage` (Повідомлення з форми):**
    
    - `id` (Primary Key)
        
    - `name` (Ім'я відправника)
        
    - `email` (Контактний email)
        
    - `subject` (Тема)
        
    - `message` (Текст)
        
    - `timestamp` (Дата і час отримання)
        
    - `is_read` (Булеве поле, за замовчуванням `False` — щоб ви могли відмічати, що вже опрацювали)
        

## Підсумок: Пріоритети для реалізації

З точки зору черговості написання коду, логіка запускається покроково:

1. Спочатку робимо **GET-маршрути** (просто віддати готові HTML сторінки).
    
2. Потім підключаємо **БД + GET** (вивести проекти з бази на сторінку).
    
3. Наостанок реалізуємо найскладніший **POST-маршрут** (обробка форми контактів, валідація, honey-pot захист та редирект із flash-повідомленням).
