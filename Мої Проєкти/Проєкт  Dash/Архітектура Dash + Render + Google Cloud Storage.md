# Схема
![[Архітектура Dash_Render_GCS.png]]

Ця архітектура побудована за принципом **розділення сховища даних (Storage) та обчислювальних потужностей (Compute)**. Вона вирішує головну проблему: як працювати з гігантським файлом на 5 ГБ, не перевантажуючи оперативну пам'ять (RAM) сервера Render і не порушуючи ліміти GitHub.

Ось покроковий розбір того, як взаємодіють елементи схеми, починаючи від розробки і закінчуючи кінцевим користувачем:

### 1. Етап підготовки та деплою (Development Workflow)

- **Код — окремо:** Ви пишете код свого Dash-застосунку локально. Сам файл `.parquet` вагою 5 ГБ **не додається** до Git. У репозиторій GitHub потрапляють лише легкі файли: `app.py`, `requirements.txt` тощо.
    
- **Авто-деплой:** Коли ви робите `git push` у GitHub, сервіс **Render** автоматично фіксує зміни, стягує свіжий код і оновлює ваш вебсервер (**Render Web Service**).
    
- **Дані — окремо:** Великий аналітичний файл (на схемі це `user_activity_log.parquet`) ви завантажуєте один раз напряму у хмару — в бакет **Google Cloud Storage (GCS)**. Це можна зробити через браузер або консоль Google Cloud.
    

### 2. Запуск та робота застосунку (Render Hosting Platform)

Коли Render успішно збирає проєкт, усередині одного процесу (контейнера) паралельно працюють два компоненти:

- **Dash Application:** Відповідає за інтерфейс користувача (кнопки, випадаючі списки, графіки Plotly).
    
- **DuckDB Analytics Engine:** Працює як «вбудований двигун» аналітики прямо всередині вашого Python-процесу.
    

### 3. Запит даних «на вимогу» (Data on Demand)

Це найважливіша частина магії DuckDB, яка рятує сервер від падіння через брак пам'яті (`OOM`):

1. **Користувач (Client)** заходить через свій браузер на сайт дашборду і, наприклад, вибирає у фільтрі конкретний місяць чи категорію товарів.
    
2. **Dash** перехоплює цю дію і передає команду до **DuckDB** у вигляді SQL-запиту:
    
    SQL
    
    ```
    SELECT date, SUM(sales) FROM 'https://storage.googleapis.com/.../data.parquet' WHERE category = 'X'
    ```
    
3. **DuckDB не завантажує всі 5 ГБ з GCS!** Завдяки поколоночній структурі файлу Parquet, DuckDB робить так званий _Column Pushdown_ та _Filter Pushdown_. Вона звертається через HTTP-запити до Google Cloud Storage і витягує з хмари **тільки ті метадані та байти**, які відповідають за потрібний стовпець (`sales`, `category`) та потрібний фільтр.
    
4. Замість 5 ГБ через мережу передається всього кілька мегабайт відфільтрованих даних.
    
5. DuckDB миттєво агрегує ці дані в оперативній пам'яті сервера (економлячи RAM), конвертує їх у легкий DataFrame та віддає Dash.
    

### 4. Візуалізація (Client & User Access)

- Отримавши відфільтрований міні-набір даних, Dash за допомогою Plotly генерує інтерактивний графік.
    
- Оновлений графік через протокол HTTPS відправляється назад у браузер користувача.
    

### Головний результат такої архітектури:

Ви отримуєте швидкість локальної аналітичної бази даних, платите мінімум (або взагалі $0, якщо вкладаєтеся у безкоштовні ліміти платформ) за хостинг Render, а ваш застосунок працює стабільно та швидко навіть під навантаженням.
