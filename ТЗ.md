
Я хочу створити невеличкий веб-додаток який буде фіксувати мої тренування/вправи з kettlebell. Він повинен бути щось накштал [Garmin Connect](https://connect.garmin.com/app/home) але для вправ з гирями та петлями TRX. У додатку повині бути такі функції:
- створювати план тренування
- вибір плану тренування та вносити фактичні дані по виконаной вправі
- звіти по тренуванням та вправам
Дякую за уточнення! Я уважно перечитав `database_schema.md` і врахував використання **Poetry**. 

Маю зауважити, що ваша ER-діаграма **дуже продумана** — особливо сподобався підхід із розділенням `WORKOUT_PLAN_SET` (план) та `WORKOUT_FACT` (факт). Це дає змогу порівнювати заплановане з фактичним, а також фіксувати реальну вагу/підходи, навіть якщо вони відрізняються від плану.

Нижче наводжу **оновлене технічне завдання** з акцентом на вашу структуру БД та інструкцію для Poetry.

# ОНОВЛЕНЕ ТЕХНІЧНЕ ЗАВДАННЯ (v2)
## Веб-додаток "Kettlebell Progress Tracker"

---

### 1. КЛЮЧОВА ЛОГІКА БАЗИ ДАНИХ (НА ОСНОВІ ERD)

Розуміння зв'язків є критичним для реалізації:

- **План (WORKOUT_PLAN)** — це "шаблон" тренування. Він містить набір запланованих підходів (`WORKOUT_PLAN_SET`), де вказано **еталонну** вправу, вагу, кількість підходів/повторень та відпочинок.
- **Факт (WORKOUT_FACT)** — це **реальне виконання**. Він прив'язаний до конкретного `WORKOUT` (сесії) та до конкретного рядка плану (`workout_plan_set_id`). 
- **Чому у FACT дублюються exercise_id та weight_id?** Це зроблено свідомо: користувач може взяти гирю на 2 кг важче або зробити на 1 підхід більше, ніж у плані. Дублювання дозволяє зберігати **історичну правду**, не змінюючи початковий план.
- **Поле `tools` у WEIGHT**: чудова ідея! Наприклад: `{ "tool": "kettlebell", "value": 16 }` або `{ "tool": "trx", "value": 0 }` (вага тіла). Це дозволяє фільтрувати вправи за типом снаряда.

### 2. ДОРОБЛЕНИЙ ФУНКЦІОНАЛ (З УРАХУВАННЯМ ERD)

#### 2.1. Сценарій "Виконання тренування" (покроково)
1. Користувач обирає `WORKOUT_PLAN` зі статусом `active`.
2. Система створює `WORKOUT` (дата, статус `in_progress`).
3. Відображаються всі `WORKOUT_PLAN_SET`, пов'язані з цим планом.
4. Для КОЖНОЇ вправи користувач бачить заплановані дані (вага, підходи, повторення) та **поля для введення факту**. При збереженні:
   - Якщо фактичні дані збігаються з плановими, можна просто скопіювати їх (щоб не вводити зайвий раз).
   - Якщо відрізняються — користувач вводить свої значення, і вони зберігаються у `WORKOUT_FACT` з окремими FK на `exercise_id` та `weight_id` (навіть якщо вони ті самі, що в плані — це нормально, це забезпечує цілісність звітів).

#### 2.2. Звіти на основі FACT-ів
- **Прогрес вправи**: будується графік (Plotly), де по осі X — дата `WORKOUT.actual_date`, по осі Y — `WORKOUT_FACT.weight_value` (або `repeat_exercise`). Дані беруться **виключно з FACT**, бо там реальна історія.
- **Тоннаж**: сума (`weight_value * repeat_exercise * number_approaches`) за тренування/період.

### 3. ОНОВЛЕНИЙ СТЕК ТЕХНОЛОГІЙ (З POETRY)

#### Backend
- **Python 3.11+**
- **Flask 3.0+**
- **Flask-SQLAlchemy** — ORM для роботи з вашою ERD.
- **Flask-Migrate** (Alembic) — для міграцій.
- **Flask-WTF** — для форм та CSRF-захисту.
- **Flask-Login** (рекомендую) — навіть для одного користувача, це дасть змогу надалі розширювати.
- **psycopg2-binary** — драйвер PostgreSQL.
- **python-dotenv** — для змінних середовища.
- **Plotly** — для генерації графіків (на сервері генеруємо JSON, на фронті рендеримо через Plotly.js).

#### Frontend
- **Bootstrap 5** (CDN).
- **HTMX** (CDN) — вся динаміка без власного JS.
- **Plotly.js** (CDN) — єдиний JS, який буде завантажено.

### 5. ПОРАДИ ЩОДО РЕАЛІЗАЦІЇ (ХИТРОЩІ З ERD TA HTMX)

#### 5.1. Як ефективно відобразити виконання (Workout Fact)
На сторінці виконання тренування використовуйте HTMX для **кожного рядка підходу**:
- Коли користувач змінює значення в полі "фактична вага" або "фактичні повторення" і виходить з поля (on blur) або натискає "Зберегти рядок", HTMX відправляє PATCH-запит.
- Сервер повертає оновлений рядок таблиці (наприклад, з зеленою галочкою, що збережено).
- Це дозволяє уникати величезних форм із купою полів.

#### 5.2. Робота з `workout_plan_set_id` у Fact
Коли ви зберігаєте факт, обов'язково передавайте `workout_plan_set_id`. Це потрібно, щоб у звіті "Виконання плану" можна було побачити: *"Заплановано 3 підходи по 10 разів, виконано 4 підходи по 8 разів (бо було важко)"*. 

#### 5.3. Валідація
- На рівні БД (PostgreSQL) рекомендую додати `CHECK`-констрейнти, що `number_approaches > 0` та `repeat_exercise > 0`, але в SQLAlchemy це можна зробити через `@validates`.

#### 5.4. Статуси
Ваша ERD має `status` у `WORKOUT_PLAN` та `WORKOUT`. Рекомендую таку градацію:
- **Plan:** `draft` → `active` → `archived`
- **Workout:** `in_progress` → `completed` | `skipped`

### 7. КОМАНДИ ДЛЯ РОБОТИ З POETRY (ШПАРГАЛКА)

```bash
# Ініціалізація (якщо починаєте з нуля)
poetry init

# Додавання основних залежностей
poetry add flask flask-sqlalchemy flask-migrate flask-wtf flask-login psycopg2-binary python-dotenv plotly pandas

# Додавання дев-залежностей
poetry add --group dev pytest pytest-flask black

# Активувати віртуальне середовище
poetry shell

# Встановити всі залежності (з poetry.lock)
poetry install

# Запуск додатку
flask --app app run
```

### 8. ЧОГО ВАРТО УНИКНУТИ (ПОМИЛКИ)

- **Не зберігайте похідні дані** (наприклад, загальний тоннаж) у БД — рахуйте його на льоту у звітах за допомогою агрегацій SQLAlchemy, це гнучкіше.
- **Не використовуйте JS для динаміки**, навіть якщо здається, що простіше. HTMX чудово справляється з додаванням/видаленням рядків форм у планах. Якщо знадобиться модальне вікно — Bootstrap має свої компоненти, які працюють з атрибутами `data-bs-*` без JS-коду.
- **Не ігноруйте поле `tools`** у Weight. Використовуйте його, щоб на сторінці звіту фільтрувати прогрес лише для гир чи лише для TRX.
